Build it yourself · Lumen + Ghost

Chisel & Studio

Type out a GUI framework and an editor shell for Lumen, file by file, from first principles. Aseprite's look, Ghost's grain, and one toolkit that hosts a pixel editor, a map editor and — eventually — a sound editor.

Layers
chisel → studio → editors
Style
Retained tree, immediate paint
Rule
One class per file
Dependencies
None

This is a hands-on build, not a tour. Each part adds one or two files, explains why they exist before showing what they contain, and ends — often — with something you can run. Nothing is imported before it is written, so if you type along in order, the program runs at every step.

Two things up front. Every language behaviour claimed here was executed against a real Ghost build rather than inferred from documentation — several of Ghost's rules are surprising, one of them badly, and the architecture below is shaped around what the interpreter actually does. And the architecture is deliberately un-clever: no service container, no dependency injection, no plugin discovery. Explicit imports and constructor arguments, because in a language with no reflection, indirection buys nothing and costs you every "where does this come from?" question.

Part 00Setup, and a window on screen

Download the Lumen binary from ghostlang.org/download and put it on your PATH. Nothing to compile: the engine, the Ghost runtime and a built-in font are all inside that one file.

A Lumen game — or in our case an application — is a folder with a main.gs in it. Make the folder and the entry file:

Three folders, three jobs, and a rule that never bends: chisel knows nothing about editors, studio knows nothing about sprites. Dependencies point one way only.

studio/ ├── main.gs the entry file Lumen looks for ├── chisel/ the GUI framework — widgets, layout, painting, input ├── studio/ the editor shell — workspace, commands, registries │ ├── sprite/ the pixel editor │ ├── map/ the map editor │ └── sound/ the sound editor, later └── resources/ fonts, icons

Lumen calls load() once, then update(dt) and draw() every frame, and hands input to optional callbacks. That is the entire contract. Type this:

A resizable 1280×800 window filled with dark grey. If Lumen complains it cannot find a game, you are one directory up — it looks for main.gs in the folder you point it at.

Name the entry file main.gs

Passing a filename explicitly (lumen main.ghost) works with any extension, but running a folder looks for main.gs exactly. And Ghost resolves import "chisel/painter" to chisel/painter.gs, so every file in this tutorial ends in .gs.

Part 01What a GUI actually is

Strip away the widgets and a graphical interface answers four questions, once per frame:

  1. Where is everything? Given a window of some size, decide the rectangle every element occupies. This is layout.
  2. What does it look like? Given those rectangles and some state, put pixels on screen. This is paint.
  3. Who gets the click? Given a point, find the element under it. This is hit testing.
  4. Who owns the drag? Once a press has started, one element keeps receiving movement until the button comes up — even outside its own bounds. This is capture, and it is the question toy GUIs forget.

There are two classic ways to arrange those answers. Immediate mode asks all four inside the draw call: if (button('Pencil')) { ... }. Nothing is stored, everything is recomputed, and layout has to be re-derived every frame from scratch. Retained mode builds a tree of objects up front and mutates it; the framework decides when to repaint.

Chisel takes the half of each that suits an editor:

Retained tree, immediate paint

The tree is retained — you declare the workspace once, fluently, and keep the objects. An editor's interface has a fixed shape: a tool bar is always a tool bar. Declaring it once means layout runs only when the window resizes, and a button can carry its own state (selected, disabled, its tooltip) without you threading it through a draw call.

Painting is immediate — paint() reads the world and draws it, every frame, with no cached render state and no invalidation bookkeeping. At 1280×800 the chrome costs a few hundred rectangles; that is nothing. The one thing expensive enough to cache is the document itself, and that gets an explicit dirty flag in part 13.

So the frame looks like this, and it never gets more complicated than this:

The four objects everything else is made of

Before any widget exists we need four things, and they are the next four parts: a Rect (where), a Theme (what colour), a Painter (how to draw a bevel), and a Widget (a node in the tree). Then a Ui to own the tree and the input state. Six files and you have a working toolkit; everything after is widgets.

Two conventions, applied from here on

  • One class per file, one trait per file, one function per helper file, named after what is inside. Free-standing functions exist only in support/ and in main.gs's engine callbacks.
  • State lives in objects, never in module variables. This is not taste — a Ghost function cannot assign to a variable outside itself (part 03 shows the trap). Instance fields are the only reliable mutable state in the language.

Part 02Rect — the unit of layout

Everything in a GUI is a rectangle being divided into smaller rectangles. Get this class right and the layout code that follows is four lines per container; get it wrong and you will be adding and subtracting stray pixels for the rest of the build.

It has one job beyond arithmetic: every rectangle is integral. Ghost's / always produces a float — 20 / 2 is a float — and a one-pixel line at a fractional y is a two-pixel smear. Rather than remembering to round at every call site, the constructor rounds and the invariant holds everywhere.

Why splitTop returns a list of two

Ghost has destructuring assignment, so [bar, rest] = area.splitTop(20) reads exactly like the sentence "take twenty off the top." The alternative — a container mutating a running area field — would work too, but this version has no state at all, which means the dock in part 09 can be re-run at any time on any rectangle and always produce the same layout. That is what makes window resizing free.

▶ Run it

Replace draw() in main.gs to prove the geometry before it matters:

import { Rect } from "chisel/geometry/rect"

function draw() {
  // That semicolon is not optional — see the note below.
  canvas.clear(color.hex('#2c2c34'));

  [bar, rest] = new Rect(0, 0, window.width, window.height).splitTop(40)

  canvas.setColor(color.hex('#3a3a44'))
  canvas.filledRectangle(bar.x, bar.y, bar.w, bar.h)

  canvas.setColor(color.hex('#191a1e'))
  canvas.filledRectangle(rest.x, rest.y, rest.w, rest.h)
}

A 40px bar across the top, a darker well below it, both exact at any window size. Resize the window and watch it hold.

If you left the semicolon off, you get syntax error: expected `]`, found `,` pointing at the destructuring line. Ghost has no newline rule, so a line starting with [ continues the previous expression — canvas.clear(...) followed by an index. End the preceding statement with ; whenever the next line opens with [ or (. It is the one piece of punctuation this language genuinely needs from you.

Part 03Theme — every colour in one object

A UI kit lives or dies on whether a colour can be changed in one place. The rule: widgets ask for roles, never shades. theme.of('button.face') survives a theme swap; color.hex('#3a3a44') sprayed through forty files does not.

The theme also owns two things that are not colours, because both change together: the UI scale (Aseprite's 1×/2×/3× setting) and the metrics — row heights, icon sizes, gutters. Metrics are stored at 1× and multiplied on read, so scaling the interface is one integer, not a hunt through the widgets.

Theme holds a palette but does not contain one — a theme file does, and a theme file is a single function that returns a configured object. That keeps one class per file and makes a new theme a twenty-line contribution.

The trap this design avoids — and it is a nasty one

In Ghost, a function cannot assign to a variable outside itself. Not "should not" — cannot, silently. This module: 

scale = 1

function setScale(n) { scale = n }

setScale(2)
console.log(scale)   // 1

…prints 1. Assignment always binds in the current environment and never walks outward, so scale = n creates a function-local that vanishes on return. There is no warning. Mutating an object works fine (map.set(), list.push(), this.field =), which is exactly why every piece of state in this toolkit lives on an instance. If you were wondering whether the class-per-file rule is dogma: it is not, it is the only thing that reliably holds state in this language.

Part 04Painter — the only file that touches the canvas

Aseprite's chrome is built from about six drawing operations, repeated everywhere. Put them in one object and no widget ever calls canvas directly, which means: the look is consistent by construction, pixel snapping happens in one place, and the day you want to render a panel into an off-screen thumbnail you hand a widget a different painter and nothing else changes.

The six, from first principles:

  • fill — a solid rectangle. Everything else is edges on top of one of these.
  • bevel — one light line on the top and left, one dark line on the bottom and right. Swap them and the same box reads as a hole. That is the entire 3D vocabulary of this interface; there are no shadows and no gradients.
  • panel — fill plus a raised bevel. The most-called function in the kit.
  • well — fill plus a sunken bevel: the canvas surround, a text field, a list.
  • groove — a dark line with a light line under it. This separator does more for the "real tool" feeling than any other single detail.
  • text — placed on whole pixels, aligned inside a rect rather than positioned by hand.
▶ Run it — the first Aseprite moment
import "lumen:window"
import "lumen:canvas"
import { Rect } from "chisel/geometry/rect"
import { Painter } from "chisel/painter"
import { asepriteDark } from "chisel/themes/aseprite-dark"

app = {}

function load() {
  window.setTitle('Studio')
  window.setMode(1280, 800)
  window.setResizable(true)

  app.theme = asepriteDark().useScale(2).loadFonts(null)
  app.painter = new Painter(app.theme)
}

function draw() {
  canvas.clear(app.theme.of('window.face'))

  painter = app.painter;

  [bar, rest] = new Rect(0, 0, window.width, window.height).splitTop(app.theme.metric('bar'))

  painter.panel(bar, null)
  painter.textIn('small', 'File   Edit   Sprite   Layer', bar.inset(6), 'left', 'middle', app.theme.of('text.normal'))

  painter.well(rest.inset(12))
  painter.groove(rest.x + 24, rest.y + 60, 200)
}

A raised menu bar with a label, a sunken well, and a groove. It already looks like a tool rather than a game — that is the bevel doing all the work. (A bare app map at the top of main.gs is the one place module-level state is fine: it is mutated through .set-style property assignment on an object, never rebound.)

Part 05Traits — behaviour you mix in

Three behaviours belong to every widget but describe none of them: the ability to run a callback conditionally, the ability to hand yourself to a callback mid-chain, and the ability to carry event handlers. In a language with interfaces you would inherit them. Ghost has traits, which are better here: a class may use several, and they compose without a hierarchy.

One trait per file, named after the trait. Member resolution order is worth remembering: the instance's own fields, then the class's own members, then its traits' members, then the superclass chain.

The loop-closure trap — this one will bite you within the hour

A closure created inside a for ... in loop does not capture the loop variable. Ghost sets the loop variable in the enclosing scope and deletes it when the loop ends, so a handler that reads it later fails with name error: `name` is not defined — at click time, far from the cause. 

// BROKEN — every handler raises when it runs
for (name in ['pencil', 'eraser']) {
  bar.add(new Button(name).on('click', function () { tools.select(name) }))
}

// CORRECT — a factory call gives each closure its own scope to capture
function selectHandler(tools, name) {
  return function () { tools.select(name) }
}

for (name in ['pencil', 'eraser']) {
  bar.add(new Button(name).on('click', selectHandler(tools, name)))
}

Any closure built in a loop needs a factory function around it. This is the single most common shape in UI code, so it is worth internalising now: closures capture scopes, and a loop body is not one.

Part 06Widget — one node, five jobs

A widget is a rectangle that knows how to divide itself, draw itself, and answer whether a point is inside it. Every control in the kit — buttons, bars, the canvas — is this class plus overrides.

Two details in here matter more than they look:

  • Every input hook is defined on the base, even though it does nothing. Ghost has no way to ask an object whether it responds to a method, and calling one that does not exist is an error — so the base class defines the whole vocabulary and subclasses override what they care about.
  • pick() walks children last-to-first, because later children are drawn on top, and the thing you can see must be the thing you click.

Part 07Ui and Pointer — the frame, and who owns the drag

Something has to hold the root of the tree and the four pointers that make an interface feel alive. That is Ui, and it is the object main.gs talks to.

PointerMeansSet when
hotunder the cursor right nowevery mouse move
activeheld downpress, cleared on release
focusedreceives keyspress on a focusable widget
capturedowns every move until the button comes upa widget asks for it

Capture is what separates a real toolkit from a demo. Press inside the canvas, drag outside it, and the stroke must keep drawing. Press a button, slide off it, release — and it must not fire. Both fall out of three rules: on press the widget may capture; while captured every move goes to it alone; on release capture drops and the click only counts if the pointer is still inside.

Now main.gs reaches its final shape. It never changes again: nine forwarding calls, and every one of them is the engine handing an event to the toolkit.

Part 08Button — five states and the slide-off rule

import { Button } from "chisel/widgets/button"
import { Rect } from "chisel/geometry/rect"

root = new Panel(null)

root.add(new Button('Pencil')

Hover it: one step lighter. Hold it: the bevel inverts. Hold, slide off, release: nothing happens — that is the rule most hand-rolled UIs get wrong. Dwell on it for half a second and the tooltip appears with its shortcut.

Note the explicit .place(): a widget with no container has to be told where it is. From the next part on, containers do that for you.

Part 09Dock — carving the workspace

Aseprite's workspace is not floating windows. Regions are carved off the edges of the available rectangle in a fixed order, and whatever survives becomes the canvas. That is why the layout holds at any window size with no hard-coded positions, and it is about twenty lines.

Why this works, and a Ghost detail that makes it possible

Blocks in Ghost do not introduce a scope. An assignment inside the switch writes to the same area the loop is using, so the running rectangle shrinks as regions are taken. In a language with block scoping this would need a different shape. It is also, precisely, the shadowing behaviour that makes a stray assignment inside an if leak to the whole function — the same rule cutting both ways.

▶ Run it — the workspace skeleton
import { Dock } from "chisel/layout/dock"

function load() {
  window.setTitle('Studio')
  window.setMode(1280, 800)
  window.setResizable(true)
  window.setVsync(true)

  theme = asepriteDark().useScale(2).loadFonts(null)

  app.ui = new Ui(theme, new Painter(theme))

  dock = new Dock()

  dock.top(new Panel('File  Edit  Sprite  Layer  Frame  Select  View  Help'), theme.metric('bar'))
  dock.top(new Panel('Sprite-0001'), theme.metric('tab'))
  dock.top(new Panel('Pixel-perfect   Alpha   Opacity 255'), theme.metric('bar'))
  dock.left(new Panel('Colours'), 96)
  dock.right(new Panel(null), theme.metric('tool') + theme.metric('gutter') * 2)
  dock.bottom(new Panel('Sprite-0001 · 32 x 32'), theme.metric('row'))
  dock.bottom(new Panel('Timeline'), theme.metric('row') * 6)
  dock.fill(new Panel(null).well())

  app.ui.mount(dock)
}

That is the Aseprite workspace, docked and resizable. Drag the window edge around: every region holds its size, the canvas takes what is left, and nothing drifts a pixel.

Want to check the arithmetic rather than trust your eyes? A dock of top 20, right 30, bottom 18 and a fill, placed into 1280×800, produces exactly this — the numbers below came out of a real run of the code above: 

menu:   [0,0 1280x20]

Note that the tool bar runs the full height below the menu bar and the status bar stops short of it — that is insertion order deciding who carves first, and it is why the menu bar is declared before everything else.

Part 10Studio — the shell, and what we deliberately did not build

Chisel is finished as a framework: rectangles, painting, widgets, input. What it cannot do is host an application — several documents, a tool that is currently selected, a command that a menu and a shortcut both invoke, preferences that survive a restart. That is the shell, and it is the studio/ layer.

The obvious move here — the one I would reach for in Laravel — is a service container: bind everything by name, resolve it anywhere, wire the app through providers. Don't. In a language with no reflection and no type hints, a container is a global hashmap with string keys, and it costs you three real things:

  • A typo becomes null at runtime, three frames from the cause. An import typo is a startup fault with a suggestion.
  • Dependencies stop being greppable. You can no longer read a file's imports and know what it touches.
  • It hides genuine cycles. Ghost's circular-import fault is a design smell detector; resolving through a container silences it without fixing anything.

What actually earns its place is smaller and more boring: one context object, constructed explicitly and passed down, plus typed registries for the things that really are looked up by name at runtime — commands, tools, file formats. A registry is not a container: it holds one kind of thing, it can validate what goes in, and its keys are user-facing anyway.

What replaced the service providers

An editor class with a boot() method — the useful half of a provider, without the two-phase dance. boot() registers tools, commands and panels; workspace(document) builds the dock for a document. Ordering is handled by the fact that you call studio.register(...) in an order you chose, in a file you can read. When the sound editor arrives it is a third register() call.

Part 11Commands and the keymap — a desktop app's routes file

Here is the one place the Laravel analogy earns its keep rather than decorating. A menu item, a tool-bar button and a keyboard shortcut are three front doors onto one action. If each owns its own copy of the behaviour, they drift: the menu says Undo is available, the shortcut disagrees, and the tooltip shows a chord that was rebound last week.

So: a Command is the unit. It owns its label, its accelerator, whether it is currently available, and what it does. Everything else refers to it by name.

Build a Studio in load(), register one throwaway command, bind it, and forward keys to the shell: 

app.studio = new Studio(asepriteDark().useScale(2).loadFonts(null))
app.ui = app.studio.ui

Press ctrl+H. Note what you get for free: the command now knows its own accelerator, so any menu row or tooltip that names 'hello' can print "Ctrl+H" without being told.

Part 12The editor chrome

Four widgets fill the dock. They are all the same two ideas — a container that arranges children, a paint method that reads state — so this part moves faster and shows the parts that are specific.

Tool bar

A column of square buttons where exactly one is selected. Selection lives in the bar, not in the buttons, so nothing ever has to "deselect the other seven".

Colour bar

A grid of swatches with a foreground and background colour under it. Rect.cell() does the arithmetic, which is why this is short — and why the grid never drifts a pixel as the panel resizes.

Menus, and why they cost almost nothing now

Because commands own their labels and accelerators, a menu row is a name. The right-hand accelerator column — the detail that makes an app feel keyboard-first before the user has learned a single shortcut — comes along for free.

Part 13The document, the tools, and the canvas

Everything so far is editor-agnostic. Now the pixel editor: a document, a tool, and the viewport that shows one and drives the other.

Ghost has no interface keyword, so a contract is a trait plus a documented set of methods — checked by the program running, not by a compiler. That is less rigorous and, in a codebase this size, entirely sufficient.

Tools

A tool is three verbs — press, drag, release — over a document. Naming note: continue is a Ghost keyword, so the middle verb is drag.

The viewport

This is the one place performance is a design question rather than an afterthought. A 128×128 sprite is 16,384 rectangles; drawing them individually every frame is how an editor ends up at 20 FPS. So the document is rendered into an off-screen Target only when it changes, and the frame blits that target at an integer zoom.

The editor that ties it together

▶ Run it — the editor draws
function load() {
  window.setTitle('Studio')
  window.setMode(1280, 800)
  window.setResizable(true)
  window.setVsync(true)

  app.studio = new Studio(asepriteDark().useScale(2).loadFonts(null))

  editor = app.studio.register(new SpriteEditor(app.studio))

  app.studio.open(new Sprite(32, 32), editor)
}

Pick a colour on the left, a tool on the right, and draw. Scroll to zoom. Drag fast and the line stays solid; drag off the canvas and back and the stroke continues, because the viewport captured the pointer on press. The checkerboard shows through where nothing is painted.

That is a working pixel editor in about nine hundred lines, of which roughly six hundred are the reusable framework.

The next optimisation, when you need it

invalidate() currently repaints the whole document. Upgrade it to take a rectangle, union the boxes touched this frame, and set the scissor to that union before repainting — a pencil stroke then costs a few dozen rectangles regardless of document size. The call sites do not change, which is the argument for having them go through one method in the first place.

Part 15Leaving room for the sound editor

The sound editor is the third tenant of this toolkit, and it is worth designing for now even though it is built last — because it drags four things into the GUI layer that a pixel editor alone would never justify, and all four turn out to be shared.

1. A time ruler, and a timeline that is not sprite-specific

Sprite frames, map animation layers and an audio waveform are the same widget: a horizontal axis with independent zoom, a playhead, and rows underneath. Build Ruler and Timeline against a small time model rather than against frames, and the sprite editor's frame strip becomes one row renderer instead of a bespoke panel.

2. Widgets that animate

A playhead and a VU meter break the assumption that the screen only changes when you touch it. Today that costs nothing — Chisel repaints every frame regardless — but the moment you add dirty-region painting, the framework needs to know which widgets cannot be skipped. Declare it now, while it is one line, rather than retrofitting it across forty widgets later:

3. Numeric scrub fields and a curve editor

A drag-to-change number field is wanted in all three editors (brush size, tile probability, ADSR times), and a curve editor serves envelopes in sound and easing in sprite animation. Both are ordinary widgets built on capture — the same three rules from part 07.

4. Splitters and persisted layout

Three editors means users will rearrange panels. A splitter is a Slider with a different paint method that writes a dock region's size instead of a value, and layout persistence is Preferences plus a named() id on each region. Neither is hard; both are near-impossible to retrofit once the dock's sizes are literals in twenty call sites — which is why Dock.edge() takes a size parameter rather than reading a constant.

The honest blocker: Lumen's audio API cannot support a sound editor yet

Today audio gives you play/stop/pause/resume/volume, and a Source adds isPlaying, setLooping, fadeIn/fadeOut, setPanning, clone, and a setPosition(angle, distance) that is spatial placement, not a playhead. An editor needs four things that do not exist:

  • Sample access — decode a file to a buffer you can read, so a waveform can be drawn at all.
  • A playhead — get and set playback position in seconds, so a scrubber can exist.
  • Loop points — start and end, not just "loop the whole thing".
  • Capture — microphone input, if recording is ever in scope.

Everything else in this part is buildable today, so build the shared widgets against the sprite and map editors, and the sound editor becomes a fourth register() call once the engine can hand it samples.

Part 16Ship it

Preferences belong in the player's own data directory, which Preferences already handles. Save them when the window closes — Lumen's quit() callback runs first, and returning true from it cancels the close, which is where an "unsaved changes" prompt eventually goes:

The finishing checklist

  • Every coordinate that reaches the canvas came from a Rect or went through snap().
  • UI scale is an integer and fonts are loaded at whole multiples of their design size.
  • Every button has a tooltip; every tooltip shows its accelerator; every accelerator comes from the command, not from a literal.
  • Press-and-slide-off does not fire. Drag outside the window keeps drawing.
  • The status bar always says where the cursor is, in document coordinates.
  • Resize the window to something absurd — 400×300, then 3000×2000. Nothing overlaps, nothing drifts.
  • Switch to the light theme early, not after a hundred colours have leaked into widget files. If it takes more than editing one theme file, a literal escaped.

LogPapercuts worth fixing upstream

✓ Every behaviour below was executed against a Ghost build, not inferred from docs

This is a working list for the language and the engine, kept with the tutorial because the design above is shaped around it. Severity is from the point of view of someone writing a GUI toolkit: high means it silently produces wrong behaviour, mid means it costs real code to work around, low means it is a surprise you learn once.

Ghost

A function cannot assign to a variable outside itselfhigh · silent

scale = 1 at module level, function set(n) { scale = n }, call it, and scale is still 1. Assignment binds in the current environment and never walks outward, with no warning. Object mutation works, so the workaround is "all state lives on an instance" — which is fine as a convention and terrible as an undocumented trap.

Would fix it assignment walks the scope chain when the name already exists, or an explicit declaration keyword makes the shadowing intentional.

Closures created in a loop cannot capture the loop variablehigh · silent until called

for (name in list) { handlers.push(function () { use(name) }) } produces handlers that raise name error: `name` is not defined when they run — the loop variable is set in the enclosing scope and deleted afterward. Every list-driven widget needs a factory function wrapper. This is the most common shape in UI code.

Would fix it a per-iteration binding, the way let behaves in JS.

Blocks do not introduce a scopehigh · doc drift

An assignment inside an if, switch or loop body writes to the enclosing function scope. This is load-bearing in Chisel's Dock.arrange() and it is also how a stray temporary leaks across a hundred-line method. Note the spec (§8.3) states the opposite — that blocks each introduce an enclosed environment — so the documentation and the interpreter disagree here.

Would fix it block scoping plus a declaration form, decided together with the two items above — they are one design question, not three.

Everything top-level is exportedhigh · design

A file cannot have a private helper beside a public class, and importing a module pulls its imports' names along for the ride. One-class-per-file makes this survivable rather than solving it.

Would fix it explicit export, with the current behaviour as the fallback for files that declare nothing.

No statics: no named constructors, no class constantsmid

Rect.fromBounds(...) and Button.HEIGHT are both impossible, so factories become free functions in helper files and constants move onto a theme object. Workable — it is why asepriteDark() is a function — but it is the single thing that most distorts library shape.

Calling a sibling method by bare name loses the receivermid · doc drift

describe() inside another method raises `this` can only be used inside a class the moment the callee touches this, even though the spec says bare sibling calls are supported. Always write this.describe(). The error also points at the callee, not the call.

A field and a method may share one namemid

With both defined, x.thing reads the field and x.thing() calls the method. Nothing warns. (I assumed the field made the method unreachable and designed around it — it does not, but one name meaning two things is still worth a diagnostic.)

A function held in a field cannot be called through the fieldmid · loud

this.guard(studio) where guard is a field holding a function raises property error: class `Command` has no method `guard` — x.field(...) parses as a method call, and method lookup does not see fields. Bind it to a local first (test = this.guard, then test(studio)). Found by this project's own test suite failing, which is the argument for having one.

Would fix it fall back to calling a callable field when no method of that name exists.

Division always promotes to floatmid

Correct, and a tax on every line of pixel layout. Rect exists partly to pay it once.

Would fix it math.floorDiv(a, b) — // is taken by comments.

Import ergonomicsmid

import "path" as name (whole module) and import name from "path" (a named export) look nearly identical and mean different things. Search paths are global and accumulate as modules load, so resolution is "first match across every directory seen so far" — two files with the same basename in different folders are a hazard. The safe rule, used throughout this tutorial: always import by full path from the project root.

Small surprises, learned oncelow

Circular imports are a hard fault (useful, but it dictates the file graph). continue is a keyword, so a tool's middle verb cannot be called that. No const. No %=; ++ is postfix only. length() is a method, and reading list.length hands you the function with no error. A line beginning with [ or ( continues the previous statement.

Lumen

No pixel writing, and no image from datahigh · blocks the pixel editor

Image has getPixel and setFilter, and that is all. A document must therefore be re-rendered as thousands of filledRectangle calls into a Target rather than written into a buffer and uploaded once. It shapes the document, undo and flood-fill design of every editor in the toolkit.

Would fix it a mutable Surface: create at a size, getPixel/setPixel, upload(), draw like an image, encode to PNG.

No file dialogs, no file drop, and no path outside the save directoryhigh

filesystem is sandboxed to the app's own save folder and Ghost's file module resolves next to the source, so opening ~/art/thing.png has no clean path. There is also no dropped-file callback. Every editor needs open and save on day one.

Audio cannot describe or seek a soundhigh · blocks the sound editor

No sample access, no playback position, no loop points, no capture. See part 15 for the minimum shape.

Target is write-only and unfilteredmid

No setFilter (only Image has it), no readback, no save. Integer zoom plus a snapped origin is what keeps pixels square, and "export PNG" has no route other than canvas.screenshot() of the whole window.

An unknown key name raises instead of answering falsemid

Good for typos in a game's isDown call; harsh for a keymap, where a mistyped binding in a data file crashes the app at the moment someone presses that key. Names are SDL scancode names ('Left Ctrl', not 'lctrl'), which is worth documenting louder.

No clipboard images, no cursor shapes, bare text inputmid

Copy-paste of a selection is table stakes in a sprite editor. Splitters want a resize cursor (drawing your own is arguably on-brand — it should still be a choice). And startTextInput gives you events, while caret, selection and the IME rectangle are yours to build.

Two small ones, and one thing that is already rightlow

There is no aligned-text primitive, so every project writes textIn() again — worth promoting into canvas. The README undersells Source, which has several methods the docs do not list. And credit where due: canvas.push('all') saves and restores the scissor box along with the transform, so nested clipping — the thing most 2D APIs make you manage by hand — already works properly.
